# Project memory

The in-process state machine passes idempotency, least-load selection, fail-and-requeue, concurrency, conversation-checkpoint, stream dispatch, and pending-entry reclaim tests. The Compose profile was validated on 2026-09-24 with Redis 7, the React test chat, and a recreated runtime container: a completed request replayed from Redis with attempt count 1. A subsequent Compose run started two Redis Streams workers; one submitted entry completed once, replayed with attempt count 1, and the `agent-workers` group reported two consumers, zero pending entries, and zero lag. A deliberately delayed worker was terminated after receiving a stream entry; a replacement reclaimed it, finalized it once, and left zero pending entries. The standalone Python command remains in-memory when `REDIS_URL` is absent. A local Compose benchmark on 2026-09-24 submitted 48 unique requests at concurrency six: all completed, client-observed p50 was 56.88 ms, p95 was 147.95 ms, throughput was 61.89 requests/s, work split evenly between two workers, and Redis Streams reported zero pending and lag after completion. It is local deterministic-stub evidence, not a production capacity claim. The `kind` profile initially failed because Kubernetes 1.37 rejects this Docker Desktop host's cgroup v1. Pinning `kindest/node:v1.31.4` produced a ready three-node cluster. On 2026-09-24, it ran Redis, one gateway, and two Redis Streams worker pods across both worker nodes; an API request completed, a duplicate replayed once, worker scale-down and scale-up succeeded, a deleted worker was replaced, and a fresh request after replacement continued the Redis-backed conversation. `infra/terraform/gcp-multicluster` and `infra/terraform/aws-multicluster` each define separate primary and secondary managed clusters and passed `init`, `fmt`, and `validate` locally; neither has received a plan or apply. `docs/cloud-deployer-identity.md` requires a dedicated, short-lived deployer identity, private Terraform state, plan review, and separate AWS and GCP contexts. Future unused `v*` tags run the release workflow, which publishes a GHCR container with SBOM and provenance; `v0.1.0` predates the workflow and has no container artifact. Cloud deployment, autoscaling behavior, and multi-cluster failover remain unproven. The `public-demo` Compose profile (`deploy/public-demo/`) was validated locally on 2026-09-25: 13 services, only nginx's 80/443 published, egress isolated to one allowlisted destination through a dedicated proxy (worker/rag-gateway have no outbound route at all), Metabase serving one approved public dashboard over the real 27,830-row `brazil-education-data-lake` v1 release (manifest-hash verified before load), both mounted Airflow DAGs paused with no import errors, and a restarted container returning to healthy unaided. A seed-script bug that mislabeled real release data as "synthetic fixture" regardless of `ANALYTICS_SOURCE` was found and fixed in that same run. Both `distributed-agent-runtime-lab` and `ai-platform-rag-observability` gained a GHCR release job (`v0.2.0`/`0.2.1`, public packages, no manual visibility flip needed); `versions.env` now pins `RUNTIME_IMAGE` and `RAG_IMAGE` by tag+digest. A same-day rerun with the real rag-platform image, the real education release bind-mounted at `EDUCATION_RELEASE_DIR`, answered a real question through nginx with a correct citation; `check_public_demo_policy.py --strict-release` now reports only `airflow` (its image bakes in DAGs from two other repos and is not itself published — expected). See `deploy/public-demo/compatibility-matrix.md`. A real VPS/domain/DNS deployment is in progress on the existing `rangeltech.net` VPS (Contabo, via `vps_rt_infra`), isolated from that VPS's other production services (Matrix bridges, Infisical) by a separate Compose project routed only through the shared Traefik's `public` Docker network.
